```typescript
export function requestCurrentAuthSession(session: AuthSession): Promise<AuthSession> {
  const config = getApiConfig();
  const request = http.createHttp();
  return request.request(buildAuthApiUrl(config.authMePath), {
    method: http.RequestMethod.GET,
    header: buildBearerHeaders(session.token),
    connectTimeout: config.timeoutMs,
    readTimeout: config.timeoutMs
  }).then((response: http.HttpResponse) => {
    request.destroy();
    if (response.responseCode < 200 || response.responseCode >= 300) {
      return Promise.reject(new Error(`${response.result}`));
    }
    return buildAuthSessionFromCurrentUserPayload(session.token, `${response.result}`);
  }).catch((error: Error) => {
    request.destroy();
    return Promise.reject(error);
  });
}
```

## 3.3 关键问题与解决方案

### 3.3.1 本地存储与后端数据同步问题

**问题描述：**
应用需要同时支持离线使用和云端同步。网络不可用时依赖本地数据，网络恢复后需与后端同步，同时要保证数据一致性和用户体验。

**解决方案：**
采用「本地优先 + 后端补充」的双写策略，实现分层降级：

1. **存储抽象层**：通过 `ProfileStorageAdapter` 接口封装存储细节，支持 Preferences 和内存两种实现
2. **后端抽象层**：通过 `ProfileBackendAdapter` 接口封装后端访问，支持 HTTP 和空实现
3. **Repository 统一调度**：`HealthProfileRepository` 作为统一入口，内部协调本地与后端

**同步流程**（来自 [ProfileRepository.ets](file:///d:/yangshengzhushou/entry/src/main/ets/services/ProfileRepository.ets#L677-L697)）：
```
加载流程：
  1. 先读取本地存储数据 → 快速呈现
  2. 尝试请求后端档案数据 → 合并更新
  3. 尝试请求后端详情数据 → 合并更新
  4. 任一步失败均回退到已有数据
  5. 最终数据写回本地存储

保存流程：
  1. 先更新内存中的 Profile 对象
  2. 尝试同步到后端 → 失败不阻断
  3. 写入本地存储 → 确保数据持久化
```

**关键设计点：**
- 本地存储始终是可信数据源，后端仅作为补充
- 任何网络异常均不影响本地功能使用
- 数据合并策略：后端数据覆盖本地同名字段
- 适配器模式便于单元测试和功能切换

### 3.3.2 天气定位的多级降级策略

**问题描述：**
天气养生建议依赖定位和天气数据，但定位权限、系统定位开关、网络状态等多种因素都可能导致获取失败，需要提供流畅的降级体验。

**解决方案：**
设计六级降级机制，每一级失败都有明确的用户提示和备选方案：

| 级别 | 场景 | 用户提示 | 数据来源 |
|------|------|---------|---------|
| 1 | 正常获取 | 显示城市+天气 | 后端天气 API |
| 2 | 定位权限未授权 | 「定位权限待开启」 | 本地默认数据 |
| 3 | 系统定位未开启 | 「系统定位待开启」 | 本地默认数据 |
| 4 | 定位坐标获取失败 | 「定位信号待获取」 | 本地默认数据 |
| 5 | 后端天气接口不可用 | 「天气待连接」 | 本地默认数据 |
| 6 | 完全离线 | 本地默认城市 | 硬编码默认值 |

**降级实现**（来自 [WeatherService.ets](file:///d:/yangshengzhushou/entry/src/main/ets/services/WeatherService.ets)）：

### 3.3.3 多角色动态 Tab 切换机制

**问题描述：**
应用支持普通用户、医生、管理员等多种角色，不同角色看到的 Tab 栏和页面完全不同。需要根据登录用户的角色动态调整界面结构。

**解决方案：**
设计角色-标签页映射服务，实现动态 Tab 渲染与权限控制：

1. **角色定义**：在 `RoleExperienceService` 中定义各角色的 Tab 配置
2. **Tab 动态渲染**：TabBar 根据角色返回的标签列表动态渲染
3. **Tab 索引校验**：切换角色时自动校正当前选中的 Tab 索引
4. **角色解析**：支持多角色用户，自动解析主角色

**核心逻辑**（来自 [Index.ets](file:///d:/yangshengzhushou/entry/src/main/ets/pages/Index.ets#L339-L359)）：
```typescript
private currentTabKey(): string {
  const tabs = this.currentRoleTabs();
  if (this.currentTab < 0 || this.currentTab >= tabs.length) {
    this.currentTab = 0;
    return tabs[0].key;
  }
  const tabKey = tabs[this.currentTab].key;
  const authorizedIndex = resolveAuthorizedTabIndex(this.primaryRole(), tabKey);
  if (authorizedIndex !== this.currentTab) {
    this.currentTab = authorizedIndex;
  }
  return tabs[this.currentTab].key;
}
```

**角色体系：**
- USER（普通用户）：首页、助手、档案、我的、问诊
- DOCTOR（医生）：工作台、问诊、个人资料
- ADMIN（管理员）：概览、用户、助手日志、问诊

### 3.3.4 网络请求候选地址轮询机制

**问题描述：**
开发和调试阶段，后端服务地址可能在多个环境间切换（真机、模拟器、局域网等），硬编码单一地址容易导致连接失败。

**解决方案：**
设计候选地址列表和自动探测机制，自动选择可用的后端地址：

**候选地址策略**（来自 [ApiConfig.ets](file:///d:/yangshengzhushou/entry/src/main/ets/services/ApiConfig.ets#L50-L56)）：
```typescript
candidateBaseUrls: [
  runtimeBaseUrl,        // 上次成功的地址（优先）
  DEFAULT_API_BASE_URL,  // 默认局域网地址
  'http://10.0.2.2:8181', // 模拟器地址
  'http://10.0.3.2:8181', // 另一模拟器地址
  'http://127.0.0.1:8181' // 本机回环地址
]
```

**轮询机制：**
1. 按优先级依次尝试候选地址
2. 第一个成功响应的地址被选为当前地址
3. 成功地址写入 `runtimeBaseUrl`，后续请求直接使用
4. 去重处理避免重复尝试相同地址

### 3.3.5 前后端数据模型适配转换

**问题描述：**
后端返回的数据结构与前端 UI 需要的数据结构存在差异，字段命名、嵌套层级、数据类型都可能不一致。需要一套清晰的适配层处理转换。

**解决方案：**
建立「后端数据 → 前端模型」的转换层，统一处理字段映射和类型转换：

**转换函数分类：**
1. **Payload → Model**：后端响应转前端模型
   - `buildAuthSessionFromBackendPayload`
   - `buildWeatherFromBackendPayload`
   - `buildHealthProfileFromBackendDetails`
2. **Model → Payload**：前端模型转后端请求
   - `buildBackendHealthArchivePayload`
   - `buildQuestionnaireAnswerJson`
3. **字段归一化**：处理可选字段、默认值、类型转换
   - `normalizeArchiveText`：字符串空值处理
   - `normalizeBackendId`：ID 类型转换（number → string）

**典型转换流程**（来自 [ProfileRepository.ets](file:///d:/yangshengzhushou/entry/src/main/ets/services/ProfileRepository.ets#L247-L265)）：
```typescript
function buildQuestionnaireFromBackendRecord(data: BackendQuestionnaireRecordData): QuestionnaireRecord {
  const totalScore = typeof data.totalScore === 'number' ? data.totalScore : 0;
  const constitutionName = normalizeArchiveText(data.constitutionType, '平和质');
  const suggestion = normalizeArchiveText(data.suggestion, '');
  const constitution: ConstitutionResult = {
    name: constitutionName,
    score: totalScore,
    suggestion
  };
  const record: QuestionnaireRecord = {
    id: normalizeBackendId(data.id),
    submittedAt: normalizeArchiveText(data.createTime, new Date().toISOString()),
    answers: buildQuestionnaireAnswersFromJson(data.answersJson),
    totalScore,
    constitution,
    suggestion
  };
  return record;
}
```

**设计收益：**
- 后端字段调整时，只需修改转换函数，不影响 UI 层
- 类型安全在转换层保证，下游代码无需处理 undefined
- 便于单元测试，转换逻辑可独立验证

### 3.3.6 认证会话持久化与有效性验证

**问题描述：**
用户登录后需要持久化会话信息，下次打开应用自动登录。但 Token 可能过期，需要处理会话失效的场景。

**解决方案：**
采用「本地持久化 + 启动校验 + 运行时缓存」三层方案：

1. **持久化存储**：使用 Preferences 将 AuthSession 序列化存储到本地
2. **启动时校验**：应用启动时读取本地会话，调用 `/api/auth/me` 验证有效性
3. **运行时缓存**：Token 保存在模块级变量 `runtimeAuthToken`，供所有请求使用

**启动验证流程**（来自 [Index.ets](file:///d:/yangshengzhushou/entry/src/main/ets/pages/Index.ets#L243-L281)）：
```
启动流程：
  1. 读取本地存储的会话
  2. 无会话 → 显示登录页
  3. 有会话 → 调用后端验证接口
     ├─ 验证成功 → 更新会话信息 → 进入应用
     └─ 验证失败 → 清除本地会话 → 显示登录页
```

**安全设计：**
- Token 仅存储在应用私有偏好设置中
- 每次请求通过 `buildAuthorizedJsonHeaders()` 统一注入 Authorization 头
- 登出时同时清除本地存储和运行时缓存
