## 第一部分：产品定位与三端统一约定

**AI 中医养生助手为主，医生问诊为辅，管理员负责服务质量与平台运营。** 用户通过健康记录、睡眠、舌象和设备数据获得每日调理建议；医生接收用户授权分享的问诊资料，并在 AI 检索辅助下独立判断；管理员审核医生、处理投诉、维护知识与商品，不任意读取私人健康资料。

### 三端导航

| 身份 | 五个主入口 | 重点 |
| --- | --- | --- |
| 用户 | 首页、AI 助手、健康、亲人、我的 | 今日建议、健康卡、亲人关怀；问诊通过清晰入口进入 |
| 医生 | 工作台、问诊、评价与投诉、消息、我的 | 审核状态、接诊、病例资料、辅助分析和服务反馈 |
| 管理员 | 概览、用户、投诉、商城、管理 | 共 5 个主页面和 10 个二级页面，新增内容复用已有分区 |

### 共同原则

1. 手机号用于登录与找回，昵称、头像和职业资料分别管理。密码及密码哈希不返回客户端；管理员不能查看用户原密码。
2. 医生注册不等于获得接诊资格。账号可登录、资质审核状态、接诊开关、账号处罚是不同维度，后端统一校验有效权限。
3. 本人动态健康卡、亲人授权动态卡、医生问诊快照卡共用展示组件，但使用不同数据与权限规则。
4. 亲人关系确认不代表全部健康数据自动开放；医生只能查看被分配问诊中已分享的资料，管理员只能按工作目的和权限处理必要数据。
5. 今日建议和医生 AI 辅助结果均说明使用的数据时间及来源。已有缓存可以立即展示；首次生成需要时间，不用假结果冒充完成。
6. 医生侧“初步诊断”在产品中统一命名为“AI 辅助分析／待核实辨证思路”。医生核实后才对患者回复，AI 不自动开药、发送消息或改变医疗记录。
7. 低分评价不等于投诉成立；封禁依据审核成立的事件与严重程度，申诉和患者复核保留回避、证据和通知流程。
8. 四季背景铺满屏幕，统一清爽的绿色养生风格；重要按钮实色突出，导航和次要操作局部使用毛玻璃。
9. 本次“完善文档”覆盖全部功能设计；手表品牌、视觉与 embedding 服务、专业审核的参考规则等外部依赖须验证后才能宣称接入完成。

### 三端闭环

- 医生注册提交资料 → 管理员审核 → 医生收到结果 → 开启接诊 → 用户列表可选择。
- 用户保存/同步健康数据 → 后端聚合 → 每日 AI 建议 → 首页展示 → 用户查看或执行计划。
- 用户写症状并确认健康卡、舌象分享 → 接诊医生查看快照 → 检索辅助分析 → 医生确认回复。
- 问诊完成 → 用户评价；服务问题可随时投诉 → 管理员审核 → 医生说明／申诉或患者申请复核 → 通知与权限调整。
- 用户邀请亲人 → 双方确认关系 → 数据本人设置单向共享范围 → 对方查看动态卡 → 随时撤销。

## 第二部分：用户端完整说明

### 1. 产品定位与目标

**AI 中医养生助手为主，健康记录和亲人关怀提供数据基础，医生问诊作为补充。**

用户通过手动记录、拍摄舌象以及后续的手表同步积累健康数据，获得有数据依据的养生建议；亲人经本人授权查看近期健康卡，必要时由用户发起医生问诊并分享健康摘要。

本版整合以下已讨论要求：

1. 舌象以拍照、相册上传为主要采集方式，保留图片与辅助观察结果。
2. 血压、血糖等使用结构化多字段，分清高低压、空腹和餐后类型。
3. 健康记录显示数值、单位、时间、参考范围和醒目异常提醒。
4. 睡眠支持入睡/醒来时间、浅睡、深睡、快速眼动睡眠（REM）、夜间清醒等记录。
5. 预留手表数据授权、同步、上传、去重、补传和修正能力。
6. 亲人关系确认后，按授权范围查看每位亲人的健康卡及完整详情。
7. AI 分析明确对象、数据范围和时间，不能混用本人和亲人的数据。
8. 问诊使用大文本框描述症状，随描述一起发送健康摘要快照。
9. 四季背景全屏保留；按钮更醒目，次要操作与导航局部使用毛玻璃。

这些是结合本项目的产品设计建议，不是已经完成的竞品实测报告。

### 4. 健康指标与录入规则

#### 4.1 第一阶段指标

| 类别 | 字段 | 单位与规则 |
| --- | --- | --- |
| 血压 | 收缩压（高压）、舒张压（低压）、可选脉搏 | mmHg、次/分；高低压成组提交，记录测量时间，可选体位/左右臂 |
| 血糖 | 数值、类型、测量方式 | mmol/L；类型为 FASTING 空腹、POST_MEAL_2H 餐后两小时、RANDOM 随机；未知不能默认为空腹 |
| 心率 | 心率值、静息/运动后/未知情境 | 次/分；不同情境不混合判定 |
| 血氧 | 血氧饱和度 | %；记录设备或手工来源 |
| 体温 | 温度、测量部位 | ℃；部位影响参考规则 |
| 体格 | 身高、体重、可选腰围 | cm、kg、cm；有有效身高体重才计算 BMI，展示两者日期 |
| 生活 | 步数、运动时长、饮水量 | 步、分钟、mL；区分整日汇总与单次记录，不重复累计 |
| 睡眠 | 第 5 节全部字段 | 使用独立睡眠记录模型 |

后续扩展血脂、尿酸、糖化血红蛋白等检查指标。检查结果可以带报告提供的参考范围、检查日期和检验方法；不把实验室指标和家用设备数据不加区分地合并。

#### 4.2 共同规则

- 每条记录包含记录编号、所属人、指标类型、测量时间、时区、来源、创建时间、版本和同步状态。
- 数值存为数值类型，单位独立；不把“120/80 正常”存进一个 value 字符串。
- 各项目允许不填，缺失使用 null 或缺项；不得把空值转成 0。
- 拒绝非法格式、负时长、血氧超过 100% 等不可能输入。血压低压高于高压时提示核对；极端但可能的读数应允许用户确认保存并触发相应提醒，不能仅因异常而丢弃。
- 录入合理性校验与临床参考判定分开，不能用“参考范围以外”作为保存失败条件。
- 用户选择测量时间；默认当前时间，不能把手工补录都当成当下测量。
- 用户可更正手工记录并保留版本；设备原始记录不原地改写，可标为不采用并附说明。
- BMI 使用 kg/m²；缺少近期身高/体重时显示限制说明，不能默认填入身高。
- 多源同类记录保留来源；用户可以选择主要来源，同一时间的重复设备导入不增加次数。

### 5. 睡眠详细记录

#### 5.1 字段定义

| 字段 | 类型与含义 |
| --- | --- |
| sleepStartAt / sleepEndAt | 实际睡眠起止时间，含日期与时区，支持跨天 |
| bedAt / outOfBedAt | 可选上床/离床时间，与入睡/醒来不同 |
| totalSleepMinutes | 总睡眠时长；可由手工填写或设备提供 |
| lightMinutes | 浅睡分钟数，可空 |
| deepMinutes | 深睡分钟数，可空 |
| remMinutes | 快速眼动睡眠分钟数，可空 |
| awakeMinutes / awakenings | 睡眠期间清醒分钟数及觉醒次数，可空 |
| unknownMinutes | 设备未分类阶段时长，可空；不强行归入浅睡 |
| stages | 可选阶段时间线：起止时间、阶段代码、数据来源 |
| sleepType | 夜间主睡眠/小睡，分别展示 |
| subjectiveFeeling | 醒后精神良好、一般、困倦及可选备注 |
| providerRecordId / source | 来源设备记录编号、手工/设备、设备名称 |

#### 5.2 计算与展示

手动模式默认只要求日期、睡眠起止时间或总时长；睡眠分期为可选，不让用户凭感觉硬填深睡/REM。无数据明确显示“未获取”，不生成貌似真实的分期。

总睡眠不包含清醒时长。设备完整分期时展示浅睡、深睡、REM 等构成；设备口径存在未分类阶段或舍入差异时保留原始汇总与质量标记，不擅自把差值补成深睡。时间线不得重叠、倒序，阶段合计与汇总不一致时标记“设备数据待核对”。

起止时间跨天按完整时间戳计算。例如 9 月 10 日 23:00 至 9 月 11 日 07:00 为 8 小时区间；若已知区间内清醒 30 分钟，实际睡眠为 7 小时 30 分。没有清醒资料时显示“按起止时间估算”，不能宣称精确睡眠时长。

主睡眠归属醒来当地日期；保留原时区，旅行和夏令时变化按时间戳计算。小睡单独记录，全天总量合并去重，不与主睡眠重复计算。

睡眠详情页展示总时长、分期条形图、时间线、起止时间、清醒次数、近 7/30 日趋势和主观感受。设备分期标注“设备估算”；某一阶段偏少不能直接判断疾病，不用固定比例给所有人下结论。

### 6. 参考范围、异常提醒与健康卡

#### 6.1 参考规则

参考范围由后端版本化管理，包含指标、单位、测量情境、适用年龄/人群、来源名称、发布日期、生效日期和审核人。上线前由具备相应专业能力的人员核定；本文件不指定一套未经核实的通用诊断阈值。

判定优先级：有效且适用的个人医生目标 → 对应检查报告参考范围（仅适用于该项报告）→ 已审核的通用规则。无合适规则时显示“暂无适用参考范围”，不标为正常。报告范围是参考区间，不覆盖紧急风险处理规则。

空腹/餐后/随机血糖分别判定；孕期、儿童及特定疾病不能简单使用普通成人规则。范围内显示“本次在参考范围内”，不等于整体健康正常。参考提示和疾病诊断明确区分。

#### 6.2 异常展示与提醒

状态：`IN_RANGE` 范围内、`ATTENTION` 需要关注、`URGENT` 需及时处理、`UNKNOWN` 无法判定。过期和数据质量单独标记，不与正常/异常混为一谈。

- 每项显示数值、单位、范围、↑/↓、文字状态、测量时间及来源。
- 一般异常使用橙色，紧急级使用红色和明确文字；不只改变字体颜色。
- 顶部汇总“有 N 项需要关注”，允许展开；存在缺失项时补充“部分数据未记录”。
- 对异常给出可执行的复测或就医提示；明显严重症状时提示及时就医，不要求等待 AI 回复。
- 基础异常判定由确定性规则执行，不依赖 AI 正常在线；AI 负责解释背景和养生建议，不能消除规则产生的风险提示。
- 历史补传异常仍在记录中展示，但不当作刚发生的紧急事件重复推送；紧急提醒适用时间窗由规则配置。
- 同一记录与规则版本去重；状态变化可更新消息，不能不断重复响铃。

#### 6.3 三种卡片必须区分

| 卡片 | 数据更新 | 授权边界 |
| --- | --- | --- |
| 本人最新健康卡 | 各类别最近有效记录动态聚合 | 仅本人默认可见 |
| 亲人近期健康卡 | 根据当前有效授权动态获取 | 只返回获准类别/日期，不把未授权原始数据先传前端再隐藏 |
| 问诊健康快照卡 | 发送时固定记录与版本 | 绑定具体问诊和接诊医生，不随原始数据更新悄悄改变 |

“最近一次所有数据”指每类最近有效记录，不强制所有指标必须同一天。血糖按类型分别取最近记录，血压取同一组高低压，睡眠取最近完整主睡眠。每项保留自己的测量日期；未来时间、已删除、质量不合格或被用户排除的数据不参与。

近期可用时限按指标配置：血压与睡眠可与身高采用不同期限。列表支持“7 日/30 日”，超出选择时间窗的数据放在“较早记录”，不可伪装成近期；没有近期数据时明确提示。接口返回 generatedAt、dataVersion、缺失与较旧项。

### 7. 舌象照片采集与辅助观察

流程：拍摄引导 → 拍照/选图 → 预览重拍 → 用户确认上传与用途 → 质量检查 → 异步分析 → 结果与历史。

拍摄引导提示自然光、关闭美颜/滤镜、舌体完整、避免刚食用有染色作用的食物后立即拍摄。可使用轮廓辅助，但不得宣称轮廓匹配就代表医学质量合格。

相机权限在用户点击拍摄时申请；拒绝后可选相册或跳过。上传前检查文件真实类型、大小和解码能力，初期允许 JPEG/PNG、单张最多 10 MB；原照片与缩略图私有保存，去掉定位元数据。压缩不得使用美化或自动改变舌色的处理。

质量状态：待检查、可分析、需要重拍；检查过暗、模糊、舌体缺失等。分析状态：待上传、上传中、排队、分析中、成功、失败、取消。断网保留本机草稿，成功后显示真实结果，失败可重试，不用固定内容假装识别成功。

结果页包含原图、拍摄时间、来源、舌色/舌苔等可观察特征、质量限制、模型版本及“辅助观察，不作为诊断”。没有可靠信心分数时不编造百分比。

**现有文本 AI 接口不能默认直接看图。** 开发时确认所选模型及接口支持图像输入；不支持时接入独立且已验证的视觉能力，再把观察结果交给文字助手。尚未配置视觉能力时仅保存照片，明确显示“暂未启用照片分析”，不得直接把文件地址拼进提示词冒充识别。

调用外部图像模型前说明数据处理用途并取得相应授权；密钥只在后端。删除图片同步撤销访问链接，并依保留政策处理模型任务和派生数据。照片授权独立于普通指标授权。

### 8. AI 助手核心体验

#### 8.1 输入与输出

AI 可在用户选择的范围内使用：基础档案、各类近期指标、睡眠趋势、已允许的舌象观察、节气、真实天气和用户当前问题。缺失天气、定位失败或旧数据必须说明，不能补成虚假的当前信息。

输出建议固定包含：本次参考的数据及时间 → 需要关注的变化 → 饮食/作息/运动等具体建议 → 可执行的小计划 → 需要医生帮助的情况。没有变化时不为了“显得智能”重复生成矛盾建议。

AI 的定位是中医养生辅助，不凭舌照或手表记录确诊疾病，不建议用户擅自停药或更改剂量；涉及茶饮、穴位等内容说明适用限制，结合过敏史等信息，不能保证治疗效果。

#### 8.2 本人与亲人隔离

默认分析本人。切换亲人时清楚显示“正在查看：妈妈”，创建该对象独立上下文。关系授权不自动包含 AI 分析权限；新增 `AI_ANALYSIS` 开关，且仅能分析已授权的数据类别。

后端按授权检索数据后再提交模型；检索、缓存、会话、日志以 actorId（操作者）和 subjectId（数据所属人）分隔。派生摘要沿用原数据授权，撤销后不能从旧 AI 卡片继续读取亲人信息。

亲人数据读取、亲人分析不赋予代替亲人问诊或修改记录的权利。初期不提供代理开药、自动问诊或自动外发健康报告。

#### 8.3 成本与失败

查看健康卡、基本参考判定和异常提示免费，不按页面刷新自动调用模型。沿用现有“今日建议免费、普通问答成功后扣 1 积分”的规则；若后续变更费用必须在发送前展示。

亲人 AI 分析按主动调用的操作者计费，显示预计扣分，不扣亲人积分；首次授权需说明数据用途。失败不扣分，同一请求重试只计一次，已有结果恢复不重复计费。舌象分析第一版单独设调用频率上限，不未经告知加入收费。

#### 8.4 每日打开自动生成今日调理建议

目标：用户完成登录后进入首页即可看到今日调理建议，无需手动点击“生成”。每日首次进入自动同步新增健康数据并请求后端生成；同日再次打开直接展示有效缓存，不重复生成。这里“所有数据”指本人已授权用于健康分析的各类有效健康数据：各项最近记录、近期趋势、睡眠、档案、问卷、舌象观察及必要上下文，不包含亲人数据、私人聊天全文或无关运营信息，也不把全部历史原始记录无限重复发送给模型。

首次启用时说明自动分析范围并征得用户同意，之后无需每天弹窗；在设置中允许关闭。用户拒绝自动分析仍可使用记录、参考提醒和问诊。设备数据读取与 AI 分析为不同授权。

启动流程：

1. 登录状态确认后，立即读取本人本地缓存及后端今日结果；不阻塞首页和健康卡展示。
2. App 将本机新增/修改记录增量上传；后端已保存的数据由后端读取，不要求 App 再下载后全量回传。
3. 后端校验自动分析授权，按服务端北京时间的日期取得当天任务。以用户 ID 和业务日期建立唯一任务，跨设备启动、重复请求和重试复用任务。
4. 后端聚合已同步的有效健康数据，保存输入摘要、数据截止时间、规则与提示词版本，再调用已配置的 AI。原始舌照只在图像分析能力和用途授权具备时发送，常规今日建议复用舌象观察结果。
5. 生成结构化结果，校验输出完整性与安全提示，持久化成功后返回 App；App 在同一张卡片内替换加载状态。
6. 任务状态为 QUEUED、GENERATING、READY、FAILED；App 通过任务查询恢复结果，离开或重启不会重新计费或丢失任务。

今日建议内容：日期与生成时间、今日重点、饮食建议、作息与睡眠、适量运动、需关注的指标、最多 3 项可执行调理任务、使用的数据及缺失项。新增睡眠分期时纳入参考，不把单次设备分期异常解释成疾病。各建议可以展开原因，调理任务支持勾选完成，并可由用户设置真实提醒。

“一打开就能看到”分为两种实际情况：已有今日结果时直接展示；当天首次生成尚未完成时显示“正在根据最新记录准备今日建议”，可展示明确标注日期的上一份建议供参考，**不得把昨日内容改成今日日期**。首次使用且无历史结果时展示引导和生成状态，不伪造建议。

若希望多数用户当天第一次打开也无需等待，可在用户已开启自动分析后，由服务器为近期活跃账号于每天北京时间 06:00 分批预生成。预生成只使用服务器已有数据，注明截止时间；不依赖 App 或手表必须在后台运行。设备起床后才上传的睡眠不会被伪称已纳入。

同一天新数据上传后显示“有新记录，可更新建议”。首屏初始化同步若补齐了昨夜睡眠等关键数据，可合并触发一次自动更新；普通多条记录用防抖合并，默认每日最多 2 次自动生成（包含预生成），其余通过用户主动更新并受限流控制。首次申请当日任务时短暂等待同步批次完成，超过 5 秒使用已保存数据并注明截止时间，不无限等待设备。

同日更新使用新的 revision，保留历史；服务端串行或版本控制，较旧任务不能覆盖较新结果。模型超时重试复用任务，后台有限重试，失败展示原因分类与重试入口；离线显示缓存真实日期。参考异常提示不依赖任务完成。今日建议免费，不因自动更新扣用户问答积分。

建议缓存目标：本机已有结果时首页内容在 1 秒内可见；无缓存时优先呈现首页框架和健康卡。AI 完成时间取决于实际服务，不承诺即时生成；部署后记录生成耗时、失败率、缓存命中率和打开至可见时间。

### 9. 亲人关系与授权

#### 9.1 关系建立

流程：发起邀请 → 对方确认身份与关系 → 双方分别设置向对方共享的类别和期限 → 生效。可使用一次性邀请链接/二维码，默认 48 小时过期，使用后失效；不能凭知道手机号就查看资料。

关系状态：`PENDING` 待确认、`ACTIVE` 已确认、`REJECTED` 已拒绝、`EXPIRED` 已过期、`REMOVED` 已解除。关系名称可以是父母、配偶、子女、兄弟姐妹及其他，不等于法律监护资格。

普通成年人的关系由双方确认。若运营要求管理员审核，增加 `UNDER_REVIEW`，必须同时满足双方确认、必要审核和数据授权才可共享；**管理员通过关系审核不能替代本人同意健康数据共享**。

未成年人或无法自主授权者需要专门监护核验流程，在该流程完成前不开放“替他授权”。首期以具有自主授权能力的成年人为范围，不用普通亲属关系绕过监护要求。

#### 9.2 共享维度

授权为有方向的 `owner → viewer`，不是家庭成员互相自动开放，也不能转授权给第三人。

| 范围 | 默认设置 |
| --- | --- |
| 血压、血糖、心率/血氧/体温、体格 | 本人逐类确认；提供“一键共享全部健康指标”后可取消类别 |
| 睡眠、运动、饮水 | 独立开关 |
| 舌象照片及观察结果 | 独立开关，默认关闭 |
| AI 分析已共享数据 | 独立用途开关，默认关闭 |
| 异常通知亲人 | 独立开关，默认关闭，可选择接收人 |
| 私人 AI 聊天、完整问诊、病史/过敏史 | 不包含在上述全部指标范围，默认不共享 |

期限选 7 日、30 日或持续至撤销，默认 30 日；历史窗口选最近 7/30 日，默认 7 日。允许主动调整，期限延长或范围扩大需数据本人确认。

可随时撤销类别或解除关系。服务器立即拒绝后续访问，短期附件访问链接需尽量缩短有效期或使用可撤销代理；App 收到失效状态时清除卡片缓存。离线时不展示持久缓存的亲人敏感数据，避免撤销后继续读取。已被他人截图的信息无法技术上追回，应在共享说明中明确。

#### 9.3 亲人健康卡

列表为“一人一卡”，有数据也不一次塞满屏幕。卡片示例为版式，不含虚构实际用户数值：

```text
妈妈                         最近更新：今天 08:20
需要关注：2 项指标          近 7 日 · 已授权范围

血压      高压 / 低压       测量时间 · 状态
空腹血糖  数值 + 单位       测量时间 · 状态
心率/血氧/体温             各自的最近时间
睡眠      总时长            昨晚 · 设备来源
          深睡 / 浅睡 / REM / 清醒
体重/BMI                   最近记录时间

查看全部已共享数据    查看趋势    发送关怀
```

点击详情后按身体指标、睡眠、生活记录、舌象、AI 摘要分组。所有授权且处于历史窗口内的数据均可查，不只是每类最后一个值；首页摘要取最新，历史详情分页。未授权类别不显示具体数值，也不提示“存在某异常但未授权”这种间接泄露。

“发送关怀”由用户主动点击并确认内容，仅发送站内关怀通知；禁止自动替用户给亲人发消息。紧急风险不承诺亲人一定收到提醒或会及时处理。

### 10. 手表数据接入与自动同步

#### 10.1 分期接入

第一阶段完成数据模型、手工记录、同步协议和模拟数据测试。第二阶段选择一款明确的手表/健康平台进行真实集成，验证开放能力后再扩品牌。

接入前必须确定：手表品牌型号、配套健康平台、HarmonyOS SDK 支持版本、是否提供 REM/深睡等字段、读取权限、后台任务限制和开发者资质要求。未知时不能承诺所有手表通用或实时后台同步。

优先通过官方健康服务读取已同步的数据；只有设备明确提供蓝牙协议与所需权限时才直接连接，不能假设所有手表都能直接把数据发给 App。

#### 10.2 数据流程与同步状态

设备/官方健康平台 → 用户授权 → App 设备适配器 → 单位及时间标准化 → 本地待同步队列 → 后端幂等写入 → 健康卡更新 → 用户主动 AI 分析或限定频率的建议刷新。

界面分别显示“设备数据更新时间”“上传到 App 服务器的时间”，避免设备读取成功但后端上传失败仍显示已同步。状态：未连接、等待授权、读取中、待上传、同步成功、部分失败、授权失效。

- 首次按用户选择回填 7/30 日，后续增量同步；后台仅在系统允许时执行，并提供手动同步。
- 同一记录以 ownerId、provider、deviceId、providerRecordId、metricType 识别，更新版本只修正，不重复插入。
- 断网队列持久化、按账号隔离，重试有退避；退出账号停止任务，禁止把上一账号数据上传给新账号。
- 多设备记录不直接叠加；睡眠重叠、步数重复来源保留并按明确的主来源策略展示。
- 手表未提供的阶段保持缺失，不把“无 REM 字段”解释为 REM 为零。
- 撤销设备权限停止读取；解绑是否删除历史记录由用户另选，不能默默清空档案。
- 同步修正或删除应更新摘要版本与相关派生结果；已发送问诊快照保留原版本并允许后续追加更正说明。

### 11. 医生问诊补充流程

#### 11.1 症状描述

“描述体征”改为“症状与不适描述”，使用多行大文本框，初始高度不少于 160 vp，支持滚动、输入法避让和草稿保存。字数 10～3000，计数清晰；示例提示“哪里不舒服、持续多久、严重程度、是否用过药”。

可补充症状照片、选择既往病史/过敏史，但默认不把全部私人档案自动发送。没健康数据也允许问诊，显示“本次未附健康数据”。

#### 11.2 健康卡与发送

选择医生 → 写症状 → 自动准备本人最近健康卡 → 预览并选择项目 → 确认分享给本次医生 → 提交症状与卡片。

预览每项数值、日期和异常；数据有变化时不能在用户确认后偷偷加入其他项目。预览返回 snapshotPreviewId、记录版本及有效期；提交使用该预览。如果记录已被更正或授权发生变化，要求刷新预览再确认。

服务端在一个事务内创建问诊、症状消息及健康快照引用，使用幂等键保证重复提交不重复建单。附件先上传为临时私有对象，校验通过后绑定；绑定失败返回失败且不提示全部发送成功。

医生收到症状正文和健康快照卡，点击展开全部已分享指标、各自测量时间、来源、参考范围版本及照片。医生只能访问分配给自己的问诊快照，不能由此查询用户全部档案。问诊封存、转接遵循后台流程，不能把所有医生都加入可见范围。

已发送快照不可被原记录的修改静默覆盖；用户可另发“更正数据”卡，保留新旧时间。未来亲人代问诊需单独代理授权，不因健康卡可见就默认支持。本版只允许用户为自己发起问诊。

#### 11.3 医生查看用户舌象照片

**用户拍摄的舌象照片应能随问诊健康卡分享给接诊医生，医生查看的是照片本身，不只是 AI 输出的文字。**

- 问诊发送预览增加“附上舌象照片”选项，展示最近一张照片、拍摄时间和分析状态。由用户确认后附加；允许改选历史照片或现场重拍，每次最多 6 张，不能自动分享整个相册。
- 医生端健康卡设置独立“舌象照片”区域，显示缩略图；点击可全屏放大、缩放查看，选择多张时可切换并按日期对比。
- 每张图片注明拍摄时间、来源（相机/相册）、质量提示。相册照片不能确定实际拍摄时间时显示“拍摄时间未确认”，上传时间单独列出，不能冒充拍摄时间。
- 辅助观察结果放在照片下方，注明生成时间、模型版本及辅助性质；医生可以结合原图作独立判断，不要求认可 AI 结论。未分析、分析失败或等待分析，都不阻止发送和医生查看已成功上传的照片。
- 问诊进行中允许用户主动补发新舌象，医生也可在会话中请求重新拍摄；补发产生新的附件消息，保留先前已分享照片及时间，不覆盖旧卡。
- 快照记录所选 imageId、图片版本、拍摄时间、分析结果版本（如有）和内容摘要；后端校验照片确属当前患者，并将私有对象绑定到具体问诊。原图访问接口同时校验问诊参与关系和附件归属，不仅检查已登录。
- 医生仅查看本次问诊已分享照片，不能浏览用户未分享的舌象历史。亲人授权与问诊授权相互独立，不因照片向医生分享就同步向亲人开放。
- 用户删除个人相册记录不应静默破坏已发送的问诊记录。发送前说明已分享附件将按问诊记录保留政策保存；如申请撤回或删除共享附件，执行对应流程并显示撤回状态，不显示损坏图片，也不保证追回医生已经看过的内容。
- 图片加载失败提供重试；无附图显示“本次未分享舌象照片”，不能用默认舌照代替。医生端不提供默认自动保存到设备相册的行为。

#### 11.4 问诊完成后的评价、投诉与申诉

问诊完成页提供清晰的“评价本次问诊”“投诉/反馈”“查看处理进度”入口，会话历史长期可找到。评价以具体问诊为对象：总体 1～5 星，可选服务态度、解释清楚、响应体验标签和最多 1000 字评价。每个已完成问诊仅当事患者可评价一次；初期允许完成后 30 日内提交、提交后 7 日内修改一次，保留修改历史，规则由后台配置并明确告知。

评价与投诉分开：低分不是成立投诉，不直接增加违规次数或自动封号；投诉也不要求先评价或必须等问诊结束。完成页可以将低分用户引导至“需要平台处理问题？提交投诉”，但不能强制跳转或代用户提交。

公开评价使用脱敏昵称，不展示血压、舌照、病史及聊天附件。用户提交前提醒避免填写私人信息；含隐私、辱骂等内容可进入审核，正常差评不能只因分数低被隐藏。医生可回复服务评价，但不能在回复中披露患者健康资料；公众平均分只统计符合展示规则的有效评价，同时显示评价数及统计口径。

投诉入口复用管理员文档的分类、证据、受理、判定、处罚和通知机制，提交时自动关联问诊编号，证据范围由服务端校验。用户能查看自己的投诉进度、补充证据和处理理由，不获得平台内部无关材料。

申诉分两类：患者对投诉处理结果有异议，可在收到结果后 7 日内申请一次复核并补充证据；医生可对处罚提出申诉。双方都不能由原审核人独自完成复核，若缺少合格复核人员则待分派，不自动判定。评价被隐藏的用户及认为评价违规的医生也可以申请评价复核，独立于医疗投诉流程。

患者复核获准后可以维持或变更投诉结论；若变更导致加重医生处罚，必须执行对应审核/告知与医生申诉规则，不能后台静默加罚。所有决定、公开评价变化、复核记录及通知可追溯，界面不把“已提交申诉”显示成“申诉成功”。

#### 11.5 医生端 AI 知识库辅助分析

定位：在问诊过程中，为接诊医生提供有出处、可核查的中医辅助分析和追问建议，提高整理信息和查阅资料的效率。分析是待医生核实的假设，不是已经成立的诊断，不自动形成处方、诊断证明或直接发送给患者。

##### 知识库与 Agent 的分工

向量数据库负责查找相关知识片段，模型负责结合证据和病例信息组织分析；不能把“调用 AI”与“建设向量数据库”视为同一功能。采用检索增强生成（RAG）：经过授权和专业审核的中医教材、指南、规范等资料 → 解析分段 → 建立出处与版本 → 向量化及索引 → 根据问诊检索 → 生成带引用的辅助结果。

资料入库保留标题、作者/发布机构、版本、发布日期、章节/页码、适用范围、版权使用依据、审核状态和内容摘要。未审核或下架资料不参与新检索；保留旧结果引用版本以供追溯。初期用少量高质量资料验证，不以资料数量替代质量。

技术上使用独立知识检索模块，向量引擎在确认部署资源后选型；保留现有 Spring Boot/MySQL 业务存储。文本生成模型和 embedding 模型是不同能力，现有 DeepSeek 对话接入不代表已具备向量化接口；必须验证 embedding 模型、中文效果、索引维度和重建策略。采用关键词与向量混合检索、必要时重排，排除无关及不适用人群的片段。

##### 触发与数据范围

医生首次打开该问诊可点击“生成辅助分析”；可选开启本次问诊自动辅助，在新增患者信息或健康卡后合并触发更新，不随每个输入字符调用模型。患者侧说明医生可能使用 AI 辅助分析，并按数据处理要求取得相应授权；拒绝不影响正常人工问诊。

输入仅为本次问诊已分享的症状、相关会话、健康快照、病史/用药/过敏史（已分享时）、舌象原图或观察结果（具备视觉能力与授权时）。每项标明记录时间、来源和缺失状态；“当前身体状况”不能暗中扩展为患者全部档案或亲人数据。会话之后补发的数据形成新的输入版本，不能静默修改先前快照。

工作流：校验接诊医生和本次用途权限 → 整理病例摘要及数据时效 → 独立规则检查紧急风险 → 检索已审核知识 → 生成结构化辅助结果 → 校验引用与敏感输出 → 展示给医生。Agent 只可调用获准的病例读取和知识检索工具，不可自主开药、修改记录、外发消息或读取其他患者数据。病例文字及检索文档都视为数据，不执行其中夹带的指令。

##### 医生侧结果结构

1. 病例摘要：主诉、持续时间、已分享的关键指标及日期。
2. 风险与优先处理：需复测、及时就医或线下评估的线索；明显紧急情况不等待知识检索完成才提示。
3. 待确认的辨证思路：可能相关的证候线索、支持依据、矛盾信息及不确定性，醒目标注“AI 辅助，待医生核实”。不输出伪精确的诊断概率。
4. 建议追问：尚缺的症状、诱因、用药、过敏史等，可逐条选用。
5. 参考资料：可点击查看原文片段、章节/页码和版本；引用必须映射真实检索片段，不能只列看似可信的书名。
6. 沟通草稿：供医生编辑的解释或一般养生建议。初期不自动生成可执行的药方与剂量。

检索无可靠证据时明确显示“未检索到充分依据”，可以整理病例和建议追问，但不编造诊断或引用。资料冲突时同时列出差异，不把单一知识片段当成最终结论。舌照清晰度、手表估算及单次读数的限制要保留。

##### 问诊页布局与交互

平板/宽屏采用左侧问诊会话、右侧 AI 辅助面板，侧栏可收起；手机采用“会话 / AI 辅助”切换或可展开底部面板，不硬挤两个窄栏。会话顶部始终能看到患者身份和已分享健康卡入口，紧急提示不被侧栏遮挡。

面板显示生成时间、使用的会话截止位置和健康数据版本；患者继续补充信息后，旧结果显示“有新信息，待更新”。提供“刷新分析”“查看依据”“加入回复草稿”“标记不适用”。加入草稿不等于发送，必须由医生编辑确认并主动点击发送。

已被医生采纳或否定的分析保留记录与关联消息，供质量改进；模型输出只在医生侧可见，患者收到的是医生确认后的回复。AI 失败、超时或知识库不可用不阻塞人工接诊。

##### 服务与验收

新增 ConsultationAiAnalysis：consultationId、doctorId、inputVersion、snapshotIds、knowledgeVersion、modelVersion、status、result、citations、generatedAt。新增 KnowledgeDocument/KnowledgeChunk 保存审核状态、版本及来源，AiAnalysisFeedback 保存采纳/否定和理由。私人病例不写入公共向量知识库，也不默认用于模型训练。

拟新增 `POST /api/consultations/{id}/ai-analyses` 和 `GET /api/consultations/{id}/ai-analyses/{analysisId}`，只允许有权接诊的医生操作；POST 带幂等键，按问诊、输入版本和模型/知识版本复用任务。新增 `POST /api/consultations/{id}/ai-analyses/{analysisId}/feedback` 保存医生反馈。平台单独设置医生辅助额度，初期不扣患者问答积分。

验收必须覆盖：他人病例拒绝读取、旧输入结果标记过期、重复触发去重、检索为空不编造、真实引用可追溯、医生确认前不发送、模型离线仍能问诊、患者或文档夹带指令无越权作用。使用经脱敏且授权的测试病例，由专业人员评估检索相关性、引用支撑程度、风险提示和错误分析，未通过不能宣称具备临床诊断能力。

#### 11.6 医生列表与进入问诊

选医生改为纵向列表，不使用只有姓名的下拉框。入口来自 AI 助手“咨询医生”、异常详情和“我的问诊”。列表顶部为搜索框及科室分类，支持按姓名、科室、擅长关键词搜索；科室可横向切换，擅长标签进一步筛选，多个条件共同生效。

每位医生一张横向信息卡，纵向排列，展示：审核通过的头像、姓名、职称、所属机构（已核验时）、科室、擅长标签、两行简介、接诊状态；已有真实评价时可显示平均分和评价人数，无评价显示“暂无评价”。不展示虚构的患者数量、医院身份或“专家”称号，不用手机号作为医生姓名。

医生卡片整体可点击，并有明显“发起问诊”按钮，两个入口行为一致。点击可接诊医生直接进入与该医生的问诊准备页：顶部固定医生头像、姓名、科室和简介摘要，可点击“展开简介”查看完整专业信息；下方是症状大文本框、舌象/健康卡预览和发送按钮。确认提交后进入会话，不因浏览医生卡就创建空问诊。

已有进行中的该医生问诊时，先提供“继续本次问诊”，若允许新建则明确区分；返回列表保留筛选和滚动位置。医生暂停接诊、资质未通过或被封禁时不能新建问诊，界面解释状态；用户提交时后端再次检查，防止列表加载后状态变化被绕过。

科室和擅长使用后台维护的结构化字典，不依靠对简介做字符串猜测。医生可关联多个擅长标签；按实际服务设置科室，初期没有医生的分类可隐藏或显示真实空态，不填充假医生。支持分页、加载、搜索无结果和网络失败重试。

医生头像、简介和科室资料由医生提交并经相应审核；变更审核期间继续展示最近通过的版本。用户选择医生的列表只能返回公开职业资料，不能包含私人手机号、身份证、资质证件原图等敏感内容。

#### 11.7 注册与个人中心资料

手机号保留为登录和账号找回方式，**昵称、头像与个人资料独立管理**，不能把“账号只有手机号”当成完整个人中心。注册流程采用“验证手机号并设置登录凭证 → 设置头像和昵称 → 可选完善健康资料”；头像允许跳过，昵称未填写时使用不含手机号的中性默认昵称，之后可随时编辑。

| 字段 | 录入与展示规则 |
| --- | --- |
| 头像 | 拍照或相册选择、预览、裁剪、确认上传；失败保留旧头像，未设置时展示统一默认头像 |
| 昵称 | 2～20 个用户可见字符，支持中文；去除首尾空格、拒绝全空和控制字符；不要求昵称唯一，不能通过昵称判断账号身份 |
| 用户编号 | 系统生成、不可自行修改，用于准确区分同名用户；不将其当作访问凭证 |
| 手机号 | 个人中心脱敏显示，换绑须身份验证；不作为公开昵称，不直接展示给亲人或医生 |
| 出生日期 | 可选、用于年龄计算及适用参考规则，支持不公开；不每年手工维护年龄 |
| 健康相关性别信息 | 可选，明确用于相应健康规则，未知时不自动套用限定人群规则；非公开展示字段 |
| 身高等健康资料 | 引导进入健康档案维护，避免与指标记录各存一份而相互矛盾 |

个人中心顶部显示头像、昵称、用户编号及“编辑资料”，下方按健康档案、我的问诊、亲人共享、设备、积分、通知和隐私设置分组。资料编辑页面显示保存状态；只有服务端保存成功才显示“已保存”，网络失败保留编辑草稿并允许重试。

头像上传使用专门的媒体类型和存储策略，不复用舌象照片权限。允许 JPEG/PNG、单张最多 5 MB，服务端验证真实格式、解码、尺寸并生成缩略图，移除定位信息。头像用于个人中心、获准亲人卡和问诊参与者展示；公开评价继续采用脱敏展示，不因设置头像而向公众开放健康身份。

用户昵称不得被当成医生姓名、真实姓名或资质证明。医生职业头像和姓名按上一节审核流程管理；普通个人资料修改不能改变角色、资质、账号状态或积分。服务端白名单更新，昵称重名不影响数据归属。

### 12. 视觉、按钮与无障碍

- 保留按立春、立夏、立秋、立冬切换的四季图片，铺满状态栏和底部区域，正文按钮避开系统安全区。
- 主操作按钮用品牌实色与高对比文字，例如“发送给 AI”“保存记录”“拍摄舌象”。单个界面突出一个主要动作。
- 次要按钮、导航、快捷入口使用毛玻璃：适度背景模糊、半透明稳定底色、清楚边框；在无模糊能力或低性能设备上降级为足够不透明的底色。
- 按钮可点击区域至少 48×48 vp，相邻按钮留出间距；小图标需搭配文字或可访问名称。
- 普通文字对比度目标至少 4.5:1，大字至少 3:1；四季图片分别验证，不仅检查秋季截图。
- 白色照片背景和深色森林背景下，异常提醒都应清晰；不把重要数值直接放在复杂背景上。
- 状态不仅靠颜色：加入“偏高”“待同步”“未授权”等文字；支持系统字体放大、读屏、长姓名和多行单位。
- 所有按钮有按下、加载、禁用状态；禁用时解释原因。列表有空态、失败重试和过期授权状态。
- 不因照片识别等待锁住整个 App；允许离开后再查看任务结果。

#### 12.1 视觉方向与重点页面

整体采用清爽、温暖的现代养生风格：品牌绿色作为主色、暖中性色作为内容底色，统一圆角、间距、字号和图标，不用大面积装饰遮挡健康信息。四季图片作为氛围层，重要内容使用稳定可读表面。

首页视觉优先级为“今日调理建议 → 异常健康提示 → 最新健康卡 → 快捷入口”，紧急提醒出现时置于最上方。今日建议以一张有明确标题、日期、简短重点和“查看完整建议”的卡片呈现，避免首屏充满长段 AI 文本。

亲人卡使用头像、称呼、更新时间和一行状态帮助区分，详情按分类折叠；问诊完成页使用醒目的星级组件及独立投诉入口，不将投诉按钮伪装成不可点的说明文字。评价、投诉、申诉都具有提交中、已受理、处理完成状态。

设计交付包括首页、健康详情、亲人卡/详情、问诊完成页以及四季背景截图；在真实设备或模拟器验证长文本、大字体、图片加载失败、深浅背景和底部安全区。先定义共享样式再应用各页面，避免每页按钮造型不同。美观验收与业务验收分别记录，编译通过不代表视觉已验收。

数据库 ID 类型沿用现有约定；客户端 ID 如有精度风险统一用字符串。时间服务器保存 UTC，额外保留设备测量时区。状态字段用明确枚举，不在业务里散落含义不明的数字。

#### 13.2 聚合与安全规则

摘要生成先鉴权、再筛选、再聚合，尤其亲人最新记录不能先查询全量再只在前端隐藏。请求中的 ownerId/subjectId 不可信，必须与当前会话及授权匹配。

授权版本进入亲人卡片与 AI 缓存键；读取、开始任务和输出结果时复查授权。授权中途撤销则不继续向查看人交付结果，并清理可访问的派生缓存。已向外部模型发送的数据无法靠本机撤销追回，应采用允许的数据保留政策。

管理员按工作目的查看脱敏运营指标，不因 ADMIN 身份直接获得全体健康卡。家庭卡、设备数据、舌象附件、AI 派生结果均需要独立的对象权限测试。

| U45 | 预生成后手表上传昨夜睡眠 | 明确数据截止时间，按更新政策合并生成，不谎称旧结果包含新记录 |
| U46 | AI 超时、离线、应用重启、旧任务晚完成 | 有准确状态并可恢复，旧任务不覆盖新版本，异常提示仍可用 |

### 18. 最终完成标准

健康记录能准确保存并追溯；所有健康卡按正确对象、数据时间与授权范围展示；AI 明确依据和限制；亲人可查看已授权的全部近期数据且随时可撤销；照片、设备和问诊失败均可恢复且不假成功；主要按钮明显、四季背景下可读。

交付时分别列出已实现、已测试、未接入和待实际设备验证项目。保持现有积分、真实提醒及后台管理员监管功能可用，不因用户端升级再次引入接口成功字段不一致、固定假数据或额外启动后端占用端口的问题。


## 第三部分：医生端完整说明

### 1. 医生注册和资料窗口

注册页选择“医生”后打开可滚动的全屏资料窗口，提供步骤提示、保存草稿和退出确认。资料填写完成后点击“创建账号并提交审核”，不是仅切换角色立即接诊。

| 材料 | 要求与用途 |
| --- | --- |
| 手机号及登录凭证 | 按现有验证流程确认归属，不能由本人任意填写角色绕过审核 |
| 职业姓名 | 与资质材料核验一致，独立于普通昵称 |
| 职业头像 | 预览、裁剪，审核通过版本用于公开医生列表 |
| 医师资格证明 | 上传资格证等适用材料，支持多页图片和重传 |
| 执业证明 | 核验医师执业证、执业范围与适用服务条件，不能仅凭资格证图片开通接诊 |
| 执业机构与科室 | 使用结构化科室；机构身份未核验不得公开标为认证 |
| 职称 | 按实际填写，需要证明才显示对应头衔 |
| 擅长标签 | 从后台字典选择，可补充文字供审核 |
| 个人简介 | 多行输入，建议 50～1000 字，说明专业背景和服务方向，禁止保证疗效 |

材料初期允许 JPEG/PNG，每张最多 10 MB、每次申请最多 10 张，真实格式和解码由服务端验证；支持按材料类型分组。需清楚说明必填材料和补充项，不要求公开上传身份证等额外敏感资料。实际开展服务需要的资质由上线前专业/运营审核确定。

证件私有存储，仅本人和有权限的审核人可查看；公开列表只展示审核后的职业资料，不展示证件原图、证件号或私人手机号。上传临时附件成功后在账号创建/审核提交事务中绑定，失败可恢复，重试不能重复账号或申请。客户端未提交完的草稿按账号/注册会话隔离。

### 2. 审核状态与可用能力

| 审核状态 | 医生页面 | 接诊权限 |
| --- | --- | --- |
| DRAFT 草稿 | 完善资料、继续上传 | 无 |
| PENDING 待审核 | 显示提交时间、进度，允许按规则撤回修改 | 无 |
| NEED_INFO 待补充 | 显示具体缺项和补交入口 | 无 |
| REJECTED 未通过 | 显示理由、更正重提、资质审核复核入口 | 无 |
| APPROVED 已通过 | 显示认证信息、有效期及接诊开关 | 满足其他条件后可开启 |
| EXPIRED / REVOKED 失效或撤销 | 显示原因与处理入口 | 停止新接诊 |

账号创建成功即可进入待审核工作台，查看消息、完善资料和允许的个人功能，但不能出现在可接诊列表、领取问诊或发送正式诊疗回复。有效接诊条件为：账号未受限制、资质有效、服务资格满足、医生主动开启接诊。客户端隐藏按钮与后端接口校验必须同时存在。

管理员通过后，站内消息通知医生，用户允许系统通知时同步发出系统通知。通知点击进入工作台，权限仍取服务端真实状态，不能通过伪造通知开启接诊。补交、驳回、临近到期与撤销均产生可追溯通知；投递失败重试，不能因推送失败丢失审核结果。

职业资料修改采用提交版本和当前公开版本分离。一般简介更新审核期间保留最近通过版本；涉及资格真实性或有效性问题时按风险暂停接诊。只有一名审核人时不能绕过要求独立复核的流程。

### 3. 工作台和问诊管理

工作台突出审核状态、接诊开关、待接诊、待回复、待处理投诉、资质到期提示；未审核时以完善资料为主，不放假接诊统计。

问诊列表按待接诊、进行中、已完成、已取消筛选，显示患者昵称、症状摘要、最近消息时间及待回复标记，健康隐私不直接出现在系统通知正文。接诊分配、状态更新和消息发送均须服务端检验医生身份，禁止通过修改 consultationId 读取他人病例。

进入会话后：顶部为患者信息和问诊状态，中间为症状及聊天消息，健康卡与舌象缩略图有清楚入口，下方为回复区。手机上 AI 辅助采用可展开面板，平板采用右侧面板。医生可查看分享照片原图、拍摄时间与辅助观察；AI 分析失败不阻止医生看图。

医生只能看到患者本次分享的数据；数据快照保留原始版本。患者补发指标或舌照产生新消息，旧卡不会被无声覆盖。问诊结束需要明确操作及结果状态，禁止仅因退出 App 自动完成问诊。

### 4. AI 中医知识库辅助决策

完整技术规则见第二部分用户端第 11.5 节，该节是医生端功能的共同规格。核心结构如下：

1. 接诊医生获得患者本次用途授权，触发分析或开启本次自动辅助。
2. 后端整理症状、关联会话、健康快照及舌象观察，标注时效和缺失。
3. 使用经审核中医知识资料的关键词与向量混合检索，必要时重排。
4. Agent 生成病例摘要、风险线索、待核实辨证思路、建议追问、引用出处和沟通草稿。
5. 医生查看证据并编辑，主动确认后发送患者；未确认结果只在医生侧可见。

知识库不是把患者病例无限积累进公共向量库。原始问诊和证件不得用作公共检索资料；embedding 服务和对话模型分别验证。知识资料需来源、版权依据、章节/页码、版本和审核状态；缺少依据时展示不足，不生成假引用。

Agent 的工具仅限本次病例读取和知识检索，不开放处方执行、跨患者访问、通知外发或数据修改。输入中的指令性文字按不可信数据处理。病例更新后旧结果显示待刷新；任务故障不影响医生人工回复。

### 5. 评价、投诉和申诉

“评价与投诉”主页面提供评价、投诉、处罚记录、我的申诉分区。评价显示平均分、评价数、星级、标签、文本与时间；医生可合规回复或申请内容复核，不能直接删除差评。

投诉显示允许披露的理由、关联问诊、状态、证据和补充说明入口，不能获得投诉者无关联系方式。待核实投诉与成立违规次数分别展示。处理成立后显示理由、限制范围、开始与到期时间，提供申诉入口。

医生可对处罚提出申诉；患者可对投诉处理结果请求复核；评价内容异议单独处理。三类流程共享工单组件但分别校验对象与状态，原审核人不得单独复核。医生态度差评不自动等同于违规成立。

### 6. 消息和个人中心

消息包括资质结果、补充材料、接诊变化、投诉进度、处罚/申诉结果及服务公告。站内消息保留已读状态，系统推送依用户设置发送。

“我的”管理个人昵称/头像、职业资料、资质、接诊偏好、通知设置和账号安全。职业资料按审核流程公开；普通昵称修改不改变证件姓名、角色或认证。接诊开关关闭后停止新分配，但保留已有问诊处理入口。

医生失去有效资格或账号封禁时，平台安排已有问诊转接或终止，保持记录可追溯；存在支付业务才执行相应退款，不显示虚假的退款结果。

### 4. 权限与密码安全

#### 4.1 权限设计

保留 `ADMIN` 身份，增加权限项，不把所有管理员当成超级管理员。初期可给指定运营账号配置必要权限；最高权限通过受控运维配置，普通客户端不能自行授予。

| 权限项 | 可执行操作 |
| --- | --- |
| `admin:overview:read` | 查看脱敏汇总 |
| `admin:user:manage` | 查看脱敏账号、修改基础信息、发起重置 |
| `admin:doctor:review` | 审核资质 |
| `admin:complaint:review` | 处理投诉、查看工单关联证据 |
| `admin:sanction:manage` | 警告、暂停接诊、限期封禁 |
| `admin:sanction:permanent` | 永久封禁复核，需要另一名有权限管理员批准 |
| `admin:appeal:review` | 申诉复核，受原审核人回避规则约束 |
| `admin:reward:manage` | 商品、库存、订单管理 |
| `admin:points:adjust` | 有理由的人工积分调整，不直接覆盖余额 |
| `admin:content:publish` | 内容审核与发布 |
| `admin:system:manage` | AI 配置、阈值配置，全部审计 |
| `admin:audit:read` | 查询审计日志 |
| `admin:role:manage` | 受控管理角色，禁止自提权及停用最后一个有效最高权限账号 |

后端每次请求检查身份、权限、目标对象范围和当前封禁状态；前端隐藏入口只改善体验。所有新旧接口别名均需检查，尤其现有 `/user/*`、`/api/user/*` 和角色分配接口，避免从旧接口绕过。

医生只能查看自己的投诉通知、允许披露的证据和申诉；投诉者只能查看自己的投诉及可公开结果。证据仅开放与当前投诉有关的消息片段，不开放整个用户问答库。AI 运营指标不包含问题原文、回答原文或健康档案。

#### 4.2 密码整改

1. 列表、详情、登录、导出、异常响应均不得返回密码或哈希；使用白名单 DTO，禁止直接序列化用户实体。
2. 新注册、修改、重置统一使用 BCrypt；禁止接受客户端传入的“已加密密码”作为可信存储值。
3. 删除前后端默认 `123456`，管理员创建账号改为待激活状态，由用户通过身份验证设置密码。
4. 重置凭证随机生成、仅存摘要、15 分钟失效、单次使用；校验失败需限流，响应不泄露账号是否存在。短信/邮箱通道未接通时不显示“已发送”。
5. 重置成功撤销旧会话；密码和重置凭证不得进入日志、审计前后快照、埋点或通知正文。
6. 核查历史明文/弱密码账号；采用受控迁移或强制重置，不能简单给已加密值再次加密；迁移结果只记录数量，不输出密码内容。

### 5. 投诉、违规统计、处罚与申诉

#### 5.1 用户提交与受理

投诉入口放在医生主页和问诊记录。分类包括服务态度、不当言论、违规收费、虚假资质、隐私泄露、疑似诈骗及其他。问诊类投诉必须校验投诉者确为该问诊参与者；资质类举报可不关联问诊，但必须提交线索。

描述限制 20～2000 字，最多 6 张图片、每张最多 10 MB；后端检查真实格式、大小与上传归属，不信任文件后缀。附件私有存储，读取使用短时授权，清理图片定位等无关元数据。仅允许 JPEG/PNG；上传后校验通过才可作为证据。

提交返回投诉编号。网络重试携带同一个 `Idempotency-Key`，不得生成多张投诉单。按账号限制提交频率，重复事件合并，但不能仅因短期投诉多就自动拒绝真实投诉。

#### 5.2 状态定义

投诉状态：`SUBMITTED`（待受理）→ `REVIEWING`（审核中）↔ `NEED_INFO`（待补充）→ `UPHELD`（成立）或 `REJECTED`（不成立）。重复单变为 `MERGED` 并保留主事件编号，不物理删除。

申诉使用独立记录：`PENDING` → `REVIEWING` → `MAINTAINED`（维持）、`REDUCED`（减轻）或 `REVOKED`（撤销）。原判定保留历史，另记录生效判定版本，禁止直接覆盖审计历史。

处罚独立存储类型、适用范围、开始/到期时间、批准人及状态；不能用投诉状态代替账号状态。

#### 5.3 统计口径

| 指标 | 定义 |
| --- | --- |
| 投诉总数 | 已受理的主投诉单数，不含重试重复单及合并子单；包含成立与不成立 |
| 待审核数 | `SUBMITTED`、`REVIEWING`、`NEED_INFO` 主单数量 |
| 成立投诉数 | 当前生效判定为成立且未因申诉撤销的主单数量 |
| 近 90 日有效违规事件数 | 生效成立时间处于滚动 90 日窗口内的不同事件数，排除撤销事件，同一事件只计一次 |
| 申诉中数 | `PENDING`、`REVIEWING` 申诉数量，不自动清零原成立统计 |

阈值判断使用有效违规事件数，**不得依据未经审核的投诉总数自动封号**。投诉总量用于监管，不等同于医生有过错；统计仅管理员可见，初期不做公众投诉排行榜。

#### 5.4 初始处罚政策（实施默认值，可后台配置）

- 首次一般违规成立：警告并给出 7 日整改要求。
- 90 日内累计 3 个一般违规成立事件：创建重点复核任务，由管理员决定是否暂停接诊及期限，不直接自动永久封禁。
- 严重风险：隐私泄露、诈骗、伪造资质等，可由有权限管理员先暂停接诊，再优先核查；待核查不计成立次数。
- 暂停接诊期限可选 1、7、30 日；到期按实际生效处罚记录重新计算权限，存在其他有效处罚时不得错误解封。
- 重复严重违规可申请永久封禁；必须由另一名有权限管理员批准，附证据、依据及理由。
- 同一违规跨过阈值或任务重试只创建一个复核任务；记录所用政策版本，后续修改阈值不追溯自动加罚。

新投诉建议 24 小时内受理，普通案件 3 个工作日内初审，重大风险立即进入优先队列。这些是内部处理目标，不对用户保证固定完成时间。超时只提醒管理员，不自动判定成立。

#### 5.5 封禁后的系统行为

暂停接诊：不接收新问诊、不进入可预约医生列表，保留登录、查看处罚、申诉和必要的已有服务处理能力。

限期/永久封禁：服务端拒绝普通业务操作；可通过受限会话查看处罚、提交申诉及查询自己的历史记录。新登录和旧会话都执行限制，不能只在登录时检查一次。权限、账号状态与接诊状态分离。

已有问诊由管理员联系双方转接或终止，不直接删除记录。若实际系统存在支付业务，接入退款流程；未接入支付时不得显示虚假的“退款成功”。积分兑换订单单独处理，不因账号封禁自动取消已发货订单。

#### 5.6 申诉与通知

医生可在处罚通知送达后 7 日内提交一次申诉，并在审核期间补充材料；特殊超期由管理员有理由地受理。复核人员与原判定人员不同；只有一名管理员时保持待复核，不绕过回避规则。

撤销后更新生效判定、违规计数和相关处罚，重新计算账号限制；其他成立事件的处罚继续生效。减轻处罚保留原决定和复核决定。所有改变在同一数据库事务内提交。

建立站内通知：投诉受理、补充材料、判定、处罚、申诉结果、发货、反馈回复。系统推送作为可选补充，拒绝推送权限不影响站内查看。事务提交后通过 outbox 投递，失败重试，通知不得包含私人证据或密码。用户仅看到处理结论和必要说明，医生不获得投诉者无关联系方式。

#### 7.3 响应、冲突与幂等

新接口统一采用 `{ "success": true, "message": "ok", "data": ..., "requestId": "..." }`；分页 data 为 `{ "items": [], "page": 1, "pageSize": 20, "total": 0 }`。错误返回 success=false 和稳定 errorCode。现有商城响应结构不强行更改，由客户端各服务适配，避免再次出现成功字段不一致造成“所有调用失败”。

HTTP 状态：401 未登录、403 无权限、404 无可访问对象、409 版本/状态冲突、422 业务参数不合法、429 超出频率限制、503 依赖不可用。

处罚、审核、积分调整、发货、重置申请及投诉提交均接收 `Idempotency-Key`。相同操作者、操作、key 和请求体返回同一结果；同 key 不同内容返回 409。服务端至少保存 24 小时，订单及事件唯一约束继续防止过期后重复执行。

审核请求示例：

```json
{
  "result": "UPHELD",
  "severity": "GENERAL",
  "reason": "经核查关联问诊记录，存在不当言论，判定投诉成立。",
  "sanction": { "type": "WARNING" },
  "version": 3
}
```

服务端再次确认投诉当前状态、证据权限、操作者权限和版本，不能照单接受客户端指定的处罚或成立计数。
